# 记忆型 Agent 的推理成本实测

一次 24 小时的真实生产观测 + 两次干预对照，回答一个问题：

**给长期在线的记忆系统（OpenViking 这类）降推理档，到底省不省钱？**

结论写在 [`REPORT.md`](./REPORT.md)，先说五条：

1. 「降推理档」在账本上通常**不省钱** —— 降到 `off`，每次请求成本反而 **+10.5%**：思考 token 归零后，预算挪去吐正文，总量几乎没变。
2. 真正省钱的是**点名关掉「不该思考的那条链路」** —— 只对一条记忆抽取链路降档，每次 **−71%**。
3. **覆盖面比幅度重要** —— 我最初的补丁只覆盖 28.65% 的调用，而 87.05% 的思考 token 在另一条被漏掉的链路上。
4. **账面变便宜 ≠ 变高效** —— 一个窗口成本低 17.85%，分解后 99.76% 来自流量搬去更便宜的平台。
5. **「24 小时」不等于「24 小时有效观测」** —— 不剔除观测缺口，速率指标能差 34%。

## 为什么公开

我按「思考 token 很贵，关掉一定省」的直觉做了三周优化，最后发现最大的一笔钱不在我以为的地方，中间还踩了几个很典型的坑：

- 金额单位错了 1000 倍（价基是「美元/百万 token」，我按「/千 token」算）；
- 补丁写好了、开关也设了，但**参数一次都没发出去**（模型名是别名，前缀白名单没匹配上）；
- 补丁只覆盖 28.65% 的调用，却拿这 28.65% 的读数去代表整体；
- 拿「窗口成本降了」当优化成果，其实 99.76% 是供应商结构变了。

这些坑不必每个人各踩一遍。觉得自己的 token 账单不对劲、又不知道钱花在哪的，可以直接抄方法，或者至少先看一眼「不要相信什么」那一节。
